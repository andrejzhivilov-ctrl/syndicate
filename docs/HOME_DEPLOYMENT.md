# Розгортання на домашньому ПК зараз, перенесення на сервер пізніше

**Дата:** 2026-10-14. **Статус:** інструкція. Жодного запуску з цього середовища не виконано: Docker у sandbox немає, тому перший запуск — на твоєму ПК, і він є першою реальною перевіркою стеку.

## 1. Коротка відповідь

**Так, можна** використати старий комп'ютер як тестовий/внутрішній стенд для стеку: `postgres`, `redis`, `vault`, `embeddings`, `eva-agent`, `n8n`, `whisper`, `nginx`. Доступ лише з домашньої мережі.

**Ні, не для 24/7 і не як продакшн:**
- Немає публічної адреси та домену: Let's Encrypt у runbook не працює, nginx піде з самопідписаним сертифікатом.
- Вимкнення живлення, сон, перезавантаження — і вечірній звіт о 21:00 пропущено (n8n не працює).
- Немає офсайт-бекапу; ПК — єдина копія даних.

**Агенти (Док, KODEX, Сем, Фін, Архітектор, Маршал, Кіра)** на будь-якому ПК поки не запускаються: Hermes-runtime в репозиторії лише як контракти (`src/agent_platform/`), образу немає. Тобто зараз розгортається **платформа + Єва**, а не агенти.

## 2. Вимоги до ПК (перевір свій ПК)

Мінімум для стеку без whisper large-v3:

| Ресурс | Мінімум | Бажано | Чому |
|---|---|---|---|
| CPU | 4 ядра x86_64 | 6+ ядер | образи x86_64; ARM може не зібратися |
| RAM | 8 ГБ | 16 ГБ | `embeddings` (BGE-M3), `postgres`, `n8n`, `whisper` |
| Диск | 60 ГБ вільних SSD | 120 ГБ SSD | образи, ваги моделей (~2 ГБ BGE-M3, ~3 ГБ whisper large-v3) |
| ОС | Ubuntu 24.04 LTS | те саме | відповідає runbook; Windows — лише через WSL2, не рекомендовано |
| Мережа | стабільний інтернет для першого завантаження | — | дальші запуски можуть бути офлайн, крім Telegram і API |

**Для whisper:** великий `large-v3` потребує ~3 ГБ RAM (ліміт контейнера `3g`). На слабкому ПК став `ASR_MODEL=small` (або `base`) у `.env`.

**Які дані мені потрібні, щоб підтвердити:** модель CPU, RAM, розмір диска, ОС і скільки годин на добу ПК працює.

## 3. Підготовка ПК

1. Ubuntu 24.04 LTS, оновлення пакетів, Docker Engine + Docker Compose v2.
2. Вимкнути сон і гібернацію (`systemctl mask sleep.target suspend.target hibernate.target`). Перевірити, що Docker стартує при завантаженні (`systemctl enable docker`).
3. Каталог даних: `sudo mkdir -p /srv/syndicate-data` і права для Docker. У `.env` задати `DATA_ROOT=/srv/syndicate-data` (за замовчуванням `/data`, як на сервері).
4. Файервол: `ufw allow from 192.168.0.0/16` (або твоя підмережа), інші порти закриті. **Проброс портів на роутері не робити.**
5. ДБЖ (UPS), якщо є. Без нього відключення світла = збій Postgres і втрата незбережених записів.
6. Бекап: мінімум — щотижневий `pg_dump` і копія `KODEX_DATA_DIR`, зашифрована, на зовнішньому диску або в хмарі (шифрування обов'язкове за `docs/DEPLOY_SYNDICATE.md`).

## 4. Запуск стеку (LAN, без домену)

```bash
cp .env.example .env            # заповнити секрети; DATA_ROOT, ASR_MODEL за потреби
sudo mkdir -p "$DATA_ROOT"/{postgres,redis,vault,n8n,whisper,embeddings,eva,nginx-certs}
docker compose up -d --build postgres redis vault embeddings eva-agent n8n nginx
docker compose ps               # очікувати healthy
bash scripts/verify_deployment.sh
```

Сервіс `whisper` можна не запускати на слабкому ПК, поки не потрібна транскрибація.

**Vault:** запускається запечатаним. Ініціалізація і розпечатування — `deploy/scripts/vault_init.sh`, `vault_unseal.sh` (див. runbook, розділ 4). Ключі розпечатування — лише у твоєму менеджері паролів, не в git і не в `.env`.

**Telegram-боти** (Док, KODEX) працюють через long polling: лише вихідне з'єднання, проброс не потрібен. Але **один токен — один споживач**: два запущені екземпляри з одним токеном дають конфлікт `409 Conflict`. Тому на час переносу токени вимикаються на старому ПК.

**Вечірній звіт о 21:00:** n8n має бути запущений. Якщо ПК вимкнений о 21:00, звіт за день пропущено. Це видно в логах n8n, а не маскується.

## 5. Перенесення на сервер (коли з'являться кошти)

Принцип: **нічого не копіюємо мовчки**. Кожен крок перевіряється окремо.

1. **Заморозити записи:** `docker compose stop eva-agent n8n`. Більше не завантажувати файли в KODEX.
2. **Postgres:** `docker compose exec postgres pg_dump -Fc -U <user> <db> > pg.dump`, зашифрувати, перенести. На сервері: `pg_restore`, потім `tests/live_pg.py` (або `bash tools/check.sh`, блок PostgreSQL).
3. **Vault: не копіювати `vault_data`.** Ключі розпечатування нового Vault будуть іншими. Новий Vault ініціалізувати на сервері, а секрети внести заново з менеджера паролів за шляхами з `src/vault_paths.py`. Політики генеруються з коду (`tools/vault_policies.py --write`).
4. **KODEX_DATA_DIR** (файли, blobs): копіювати з перевіркою SHA-256 і шифруванням у транзиті. Відновити права каталогу; він поза git.
5. **n8n:** експортувати воркфлоу з `n8n_data`; cron-шаблони є в `src/n8n_templates.py` (21:00 — `/proactive/evening`).
6. **`.env`:** створити на сервері заново. Не переносити через git і не передавати в чаті.
7. **Один екземпляр з Telegram-токеном.** Спочатку зупинити боти на домашньому ПК, потім запускати на сервері. Інакше `409 Conflict`.
8. **DNS і TLS:** домен, `bash deploy/scripts/setup_ssl.sh` (Let's Encrypt). Порт 80 має бути відкритим для certbot.
9. **Перевірка:** `bash tools/check.sh` (зелено), `bash scripts/verify_deployment.sh`, і вручну один запит до `/health` і одна кнопка Telegram.
10. **Ввести в дію домашній ПК як бекап-вузол** або вимкнути (за рішенням Андрія).

## 6. Розмір сервера (оцінка, не вимірювання)

`deploy/RESOURCE_CALCULATION.md` розраховано на **повний** план із 23 контейнерами і 48 ГБ RAM. Для поточного стеку (8 сервісів) це завищено. Орієнтир для поточного стеку: **4 vCPU, 16 ГБ RAM, 100 ГБ SSD**, з `whisper` на `small`. Це оцінка за лімітами й типовими образами. Справжні цифри з'являться після першого запуску на ПК (`docker stats`), і їх треба перевірити перед тим, як вибирати тариф.

## 7. Що НЕ робимо з домашнього ПК

- Не вмикаємо проброс портів і публічний доступ.
- Не запускаємо агентів (вони не реалізовані).
- Не зберігаємо секрети в git, `.env` не комітимо.
- Не використовуємо домашній ПК як єдину копію даних.
