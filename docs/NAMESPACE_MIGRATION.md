# Бренд і міграція технічних просторів імен

**Назва системи:** **Синдикат** (`SYNDICATE`). Єва — окрема агентка/профіль; це не назва платформи.

Цей документ описує підготовлену, але **не застосовану до live-середовища** міграцію технічних ідентифікаторів. Сервер, Vault, PostgreSQL і контейнери під час підготовки не запускалися та не змінювалися.

## Канонічні назви й перехідна сумісність

| Поверхня | Канонічне значення | Перехідний стан |
|---|---|---|
| UI, API-метадані, документація | `Синдикат` / `SYNDICATE` | Старі історичні записи не переписуються як факти минулого. |
| Vault KV v2 | `secret/data/syndicate/...` | Читання спершу пробує новий шлях, а лише на **HTTP 404** переходить до старого `secret/data/eva-syndicate/...`. Для runtime-політик згенеровано точкові grants під обома префіксами. |
| PostgreSQL database | `syndicate` | `eva_syndicate` лишається джерелом для контрольованого перейменування на місці; старі live `.env` не змінюються автоматично. |
| GitHub clone URL у runbook/bootstrap | `andrejzhivilov-ctrl/syndicate` | Робоча гілка цієї сесії не змінюється. |

Назви агентів/служб на кшталт `eva-agent`, профіль `eva`, `EVA_DATA_DIR` та обліковий запис БД `eva` залишаються технічними ідентифікаторами Єви/існуючого runtime, а не брендом усієї системи. Telegram bot handle-и також не перейменовуються кодом: зміна самого акаунта потребувала б окремого рішення.

## Vault: копіювання секретів без видалення

Код у `src/vault_paths.py` використовує `syndicate` як канонічний префікс. `VaultClient` читає новий шлях першим і звертається до legacy-шляху тільки коли новий повертає 404. Помилка авторизації (`403`), мережевий збій чи інша помилка не приховується fallback-ом.

`config/vault/policies/*.hcl` генеруються з точковими grants для обох префіксів. Це тимчасова сумісність у репозиторії; **політики у live Vault не застосовувалися**. Agent runtime tokens не мають прав, потрібних для повної міграції.

### Операторський запуск (не виконувався)

1. Запланувати вікно обслуговування та зробити перевірений Vault snapshot/backup.
2. Через захищений канал надати операторському токену тільки потрібні `LIST`/`READ` для старого префікса та `READ`/`CREATE` для нового. Не використовувати runtime AppRole токен.
3. У захищеному середовищі встановити `VAULT_ADDR` і `VAULT_TOKEN`, не передаючи їх у аргументах, логах чи Git.
4. Запустити спершу dry-run:

   ```bash
   python tools/migrate_vault_namespace.py
   ```

   Dry-run **читає** активні секрети, але не пише їх; у виводі є лише підсумок і шляхи.
5. Перевірити список конфліктів/обсяг через контрольований операторський процес. Якщо все погоджено, окремо запустити:

   ```bash
   python tools/migrate_vault_namespace.py --apply
   ```

   Інструмент копіює тільки відсутні destination values із KV CAS `0`, спершу перевіряє весь набір, зупиняється на destination-конфлікті й **ніколи не видаляє** джерело та не перезаписує наявний destination. При частковій помилці старі значення лишаються; повторний запуск ідемпотентний для вже скопійованих однакових значень.

Інструмент переносить лише актуальний data payload. Історія версій KV v2, часові мітки та custom metadata автоматично не копіюються; якщо вони потрібні, міграцію слід доповнити окремо до запуску. Після копіювання перевірити читання цільових шляхів і лише потім розглядати видалення legacy grants/fallback окремою погодженою зміною. До такого рішення обидва простори лишаються доступними.

## PostgreSQL: контрольоване перейменування бази

Нові приклади конфігурації та Compose default використовують `POSTGRES_DB=syndicate`. Для чинного розгортання значення в уже наявному `.env` лишається джерелом істини до окремої міграції; заміна лише Compose default не перейменовує БД у persistent volume.

`tools/migrate_postgres_db_name.py` виконує тільки каталогове перейменування, без копіювання рядків або зміни схеми. Dry-run є типовим режимом; він перевіряє стан бази й активні сесії. Для live запуску потрібен окремий операторський дозвіл:

1. Перевірити відновлюваність backup і зупинити API та всі workers.
2. У захищеному середовищі задати `SYNDICATE_POSTGRES_ADMIN_URL` — DSN адміністратора, підключений саме до службової БД `postgres`; не записувати його в Git/чат/логи.
3. Запустити preflight: `python tools/migrate_postgres_db_name.py`.
4. Лише за окремим дозволом виконати: `python tools/migrate_postgres_db_name.py --apply`.
5. Інструмент відмовляється продовжувати за активних з'єднань і сам їх не завершує; він блокує нові підключення на час перевірки, перейменовує БД на місці та знову дозволяє підключення. Після успіху оновити захищений `.env` на `POSTGRES_DB=syndicate`, перевірити readiness/backup і тільки тоді запускати сервіси.
6. Для контрольованого повернення старої назви передбачено `--rollback --apply`; перед rollback знову потрібні backup, зупинка workers і відсутність активних сесій.

Якщо запуск застосування завершився помилкою, перевіряти стан тільки через захищений операторський канал; не запускати скрипт повторно навмання.

## Що зроблено тут

- Людинозрозумілі заголовки/метадані приведені до `Синдикат` / `SYNDICATE`; GitHub URL оновлені до чинного slug `syndicate`.
- Vault і PostgreSQL код/приклади переведені на нові канонічні назви з перехідною сумісністю та окремими інструментами міграції.
- Усі інструменти мають тестові fake transports/DB-API stubs; жодних live secrets чи підключень не потрібні для unit tests.
- Не змінювалися `docs/archive/`, старі записи в `docs/HANDOFF.md` і захищений журнал повного діалогу. Старі історичні назви у них не визначають сучасний бренд системи.
- Жодна політика не була застосована у Vault; жодна БД не перейменована; ніякий server/container не запускався.
