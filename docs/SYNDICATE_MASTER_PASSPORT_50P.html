3.2. Redis 7.2 (Оперативна та Сесійна Пам'ять)

Redis працює у пам'яті (in-memory) з увімкненим скиданням на диск AOF (Append Only File) для відмовостійкості:

  • Оперативні сесії (TTL 24 години): Зберігає живий контекст діалогів Андрія з Євою та Кірою. Ключі виду session:{agent_id}:{user_id}.
  • Блокування ідемпотентності (Idempotency Locks): Ключі idempotency:{request_hash} із часом життя 300 секунд. Запобігають подвійним списанням коштів або повторному відправленню ордерів при мережевих ретраях.
  • Кеш гарячих уроків: Ключі lessons:{agent_id}:recent містять останні 20 зафіксованих помилок агента для миттєвого інжектування в промпт без звернення до Postgres.

3.3. HashiCorp Vault (Центральне Сховище Секретів KV-v2)

Усі секрети зберігаються виключно у Vault. Зберігання API-ключів у відкритих файлах .env або вихідному коді карається негайним падінням тестів CI.

  • Єдине джерело шляхів: Модуль src/vault_paths.py чітко визначає шляхи читання секретів, наприклад: secret/data/syndicate/agents/fin/integrations.
  • Механізм AppRole: Кожен контейнер директора при старті отримує власний унікальний RoleID та SecretID, що дає доступ виключно до власних ключів (Principle of Least Privilege).
  • Процедура розпечатування (Unsealing): У продакшені Vault ініціалізується з 5 ключами Shamir (поріг 3 ключі для розпечатування). Ключі зберігаються у Андрія офлайн.

3.4. Локальний Сервер Ембеддингів BGE-M3 (1024 Виміри)

Для векторного пошуку використовується державна топова open-source модель BAAI/bge-m3, розгорнута в окремому ізольованому контейнері deploy/runtime/embeddings_server.py.

  • Параметри: Довжина контексту до 8192 токенів, вихідна розмірність 1024 виміри, підтримка щільного (dense) та розрідженого (sparse) пошуку.
  • Нуль витрат ($0.00): Повна незалежність від OpenAI Ada-002 / Text-Embedding-3. Векторизація терабайтів знань Arena Knowledge Pool відбувається локально без витрат бюджету.

  1. М'яка Пауза: Процес тимчасово заморожується в оперативній пам'яті (без примусового kill).
  2. Внутрішній Допит: Маршал ініціює швидкий JSON-RPC діалог з агентом: «Яка мета цієї дії? Який математичний очікуваний результат?»
  3. Ескалація Ініціативи: Якщо аргументація логічна — Маршал відправляє Андрію в Telegram картку ініціативи з двома кнопками: [Ухвалити та додати до політики] або [Відхилити та занести в Lessons Layer].

РОЗДІЛ 7. Системні Протоколи та Оркестрація (`src/`)

7.1. Центральний Оркестратор LangGraph (`src/orchestrator.py`)

Будь-який запит користувача чи системна подія обробляється скінченним автоматом графів LangGraph:

Вхідний Запит / n8n Webhook │ ▼ [Router Node] ────────► Визначення цільового директора (eva, fin, sam, doc, architect...) │ ▼ [Lessons Check] ──────► pgvector пошук минулих помилок у memory.lessons (BGE-M3) │ ▼ [Agent Execution] ────► Виконання задачі domain worker'ом (Python / LLM) │ ▼ [Confidence Gate] ────► Оцінка впевненості агента (src/confidence.py ➔ ACT / ASK / REFUSE) │ ▼ [Outbound Veto] ──────► Перевірка Sentinel'ом безпеки вихідних дій (блокування delete, direct mail) │ ▼ [HITL Gate] ──────────► Якщо requires_hitl=True ➔ відправка інлайн-кнопок Андрію в Telegram │ ▼ [Finalize & Save] ────► Запис епізоду в memory.episodes, оновлення Redis сесії

7.2. Движок Довіри та Ескалацій (`src/confidence.py`)

Уніфікований бюджет довіри виключає самовільні помилки:

Рівень Умова Спрацьовування Дія Системи
ACT Confidence >= act_threshold та ризик дії = low Дія виконується автономно без турбування Андрія. Заноситься в лог.
ASK Confidence між ask_threshold та act_threshold, або ризик = high Виставляється прапор requires_hitl: True, формується запит у Telegram.
REFUSE Confidence < ask_threshold або дія у списку заборонених Повна відмова у виконанні з поверненням аргументованої причини.

Базові пороги директорів: СЕМ: act=1.0 (ніколи сам), ask=0.0 (завжди питає); ДОК: act=0.85, ask=0.50; ФІН: act=0.85, ask=0.50; АРХІТЕКТОР: act=0.75, ask=0.40; ЄВА: act=0.80, ask=0.45.

7.3. Шар Уроків Холдингу (`src/lessons.py`)

  • Перед виконанням нової дії оркестратор проводить косинусний пошук: якщо схожість з минулим негативним досвідом > 0.72 — дія блокується або супроводжується попередженням prior_lessons.

7.7. Патерн Розподілених Транзакцій (Distributed Saga Orchestration)

Оскільки операції Синдикату часто зачіпають декілька незалежних сервісів (банк, біржа, база даних, CRM, Telegram), оркестратор використовує патерн Saga:

  • Компенсуюча транзакція (Rollback): Якщо на Кроці 3 виникає помилка мережі, оркестратор автоматично викликає зворотні методи: Крок 2-Rev (Анулювання ТТН Нової Пошти) та Крок 1-Rev (Зняття резерву коштів у казначействі Фіна).
  • Ніяких «завислих» грошей або напівстворених замовлень у системі не допускається.

8.1. Архітектура Голосового Тракту (`src/voice/`)

  • AudioCache (Кешування аудіо): Redis-кеш на базі SHA-256 хешу тексту та ID голосу. Стандартні статусні фрази («Так точно», «Запит прийнято», «Брифінг сформовано») відтворюються за 5 мс без звернення до хмарних API, заощаджуючи баланс.

РОЗДІЛ 9. Автоматизація n8n, 4 Золоті Шаблони та Бойовий Розклад

Платформа n8n є головною нервовою системою низькорівневої автоматизації Синдикату. Вона звільняє директорів від рутинних HTTP-запитів, трансформацій JSON та механічної синхронізації з зовнішніми сервісами.

9.1. Архітектура Кластера n8n

  • Образ та Режим: n8nio/n8n:1.60.0, розгорнутий у Docker Compose з окремим томом /home/node/.n8n.
  • База даних метаданих: PostgreSQL 16 (схема n8n_core), що забезпечує транзакційну надійність при збереженні станів воркфлоу.
  • Черга та Масштабування: Режим черг (Queue Mode) через Redis 7.2 з підтримкою воркерів для важких задач обробки медіа.
  • Безпека: Всі вебхуки закриті автентифікацією через HMAC-SHA256 підпис або Bearer-токени з HashiCorp Vault.

9.2. Чотири Золоті Шаблони Синдикату (Syndicate Golden Templates)

Кожен воркфлоу, що додається до Синдикату, зобов'язаний бути побудований на базі чотирьох стандартизованих шаблонів:

📐 ЗОЛОТИЙ ШАБЛОН 1: Глобальний Обробник Помилок (`syndicate_error_handler.json`)

Гарантує, що жоден збій не залишиться непоміченим і не зависне в «сірій зоні»:

  • При перехопленні статусу error у будь-якому вузлі воркфлоу формується структурований пакет: workflow_id, node_name, execution_id, error_message, timestamp, input_payload.
  • Пакет записується в PostgreSQL memory.episodes із категорією incident та критичністю HIGH.
  • Надсилається екстрений алерт у Telegram-канал #syndicate-sentinel із червоною плашкою та посиланням на лог у Grafana.
  • Ініціюється автоматичний відкат транзакції (компенсуюча транзакція Saga), якщо впав один із етапів фінансового чи торгового ланцюжка.
📐 ЗОЛОТИЙ ШАБЛОН 2: Ідемпотентний Вебхук (`syndicate_idempotent_webhook.json`)

Унеможливлює повторне списання грошей, дублювання повідомлень або подвійне відкриття біржових позицій при мережевих тайм-аутах:

  • Кожен вхідний запит зобов'язаний містити унікальний заголовок X-Syndicate-Request-ID (UUIDv4).
  • Першим вузлом n8n виконує команду Redis SETNX syndicate:idemp:<request_id> 1 EX 86400.
  • Якщо ключ уже існує (відповідь 0): ланцюжок негайно зупиняється і повертає HTTP 200 {"status": "duplicate_suppressed"} із попередньо збереженим результатом.
  • Якщо ключ новий (відповідь 1): запит іде в основний пайплайн виконання.
📐 ЗОЛОТИЙ ШАБЛОН 3: Політика Повторних Спроб з Джиттером (`syndicate_retry_policy.json`)

Захист від тимчасових мережевих збоїв зовнішніх API (Google, Binance, Novapost, Monobank):

  • Експоненціальний відкат (Exponential Backoff): інтервали 1s, 2s, 4s, 8s із додаванням випадкового джиттеру (+-250 мс) для запобігання thundering herd.
  • Максимальна кількість спроб — 3.
  • У разі трьох поспіль відмов — автоматичне перемикання (Failover) на резервного провайдера (наприклад, з Groq на OpenAI, або з Monobank на ПриватБанк).
📐 ЗОЛОТИЙ ШАБЛОН 4: Динамічний Міст Vault (`syndicate_vault_bridge.json`)

Жодних відкритих API-ключів у JSON-файлах воркфлоу чи змінних середовища n8n:

  • Перед виконанням вузла, що вимагає авторизації, n8n звертається до локального Vault за адресою http://127.0.0.1:8200/v1/secret/data/<agent_path> з коротким AppRole токеном.
  • Секрет зчитується в оперативну пам'ять вузла, використовується для виклику REST API і негайно витирається з пам'яті.
  • Логи n8n підлягають автоматичній десенсибілізації: ключі не відображаються у вікні Execution History.

9.3. FlowLint — Статичний Валідатор Воркфлоу

Перед деплоєм будь-якого нового воркфлоу в репозиторій запускається лінтер tools/flowlint.py, що перевіряє:

  • Відсутність хардкоджених токенів, паролів та IP-адрес (regex-сканування).
  • Наявність вузла Global Error Trigger у кожному ланцюжку.
  • Відповідність стандарту найменування вузлів (наприклад: [SRC] Fetch Monobank, [VAL] Check PII, [SINK] Save Postgres).
  • Наявність тестового набору даних (Mock Payload) для автоматизованого CI/CD тестування.

12.1. Архітектура Підключення та Транспортні Протоколи

Синдикат підтримує два офіційні транспортні стандарти MCP:

  • Stdio Transport (Локальний процес): Запуск локальних Docker-контейнерів або Node.js/Python процесів із передачею JSON-RPC через стандартні потоки stdin/stdout. Забезпечує нульову мережеву затримку (<2 мс) та максимальну безпеку (відсутність відкритих мережевих портів).
  • Streamable HTTP / SSE Transport (JSON-RPC over HTTP/SSE): Підключення до віддалених або захищених мікросервісів через Server-Sent Events та HTTP POST. Вимагає обов'язкової mTLS або Bearer-автентифікації через HashiCorp Vault.

РОЗДІЛ 13. Інженерний Регламент, Правила AGENTS.md та Ворота check.sh

Синдикат функціонує за армійським принципом непорушної субординації, стандартів якості коду та суворого інженерного комплаєнсу. Усі агенти, розробники та допоміжні скрипти підпорядковуються положенням протоколу AGENTS.md та проходять автоматичні ворота якості tools/check.sh.

13.1. Звід Законів Розробки `AGENTS.md`

  • Повна Типізація: Кожна функція та метод зобов'язані містити повні тайп-хінти Python (type annotations) та pydantic v2 моделі для валідації payload. Відсутність типів карається блокуванням коміту.
  • Заборона «Магічних Стрічок» та Хардкоду: Жодних відкритих секретів, паролів чи ендпоінтів. Усі значення отримуються або через змінні оточення pydantic Settings, або динамічно через Vault AppRole.
  • Структуроване Логування (structlog): Усі логи пишуться в JSON-форматі з обов'язковими полями agent_id, action, correlation_id, latency_ms, status. Жодних викликів звичайного print() у бойовому коді.
  • Покриття Тестами >90%: Будь-який новий модуль чи зміна логіки директора не приймаються без супровідного pytest-файлу, що тестує позитивні, негативні та граничні сценарії.
  • Принцип Найменших Привілеїв (PoLP): Контейнери працюють під непривілейованим користувачем (UID 1001), без доступу до docker.sock хоста.
