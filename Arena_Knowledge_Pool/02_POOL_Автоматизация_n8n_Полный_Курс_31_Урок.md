## Урок 01: Введение в курс и знакомство с n8n
**Модуль:** `1` | **Цель:** Познакомиться с архитектурой платформы n8n, логикой low-code автоматизаций и ключевыми отличиями от классического программирования.
**Ключевые узлы:** `Start / Manual Trigger`, `Set (Edit Fields)`, `NoOp`

### Теория и механика:
n8n (nodemation) — это расширяемая open-source платформа автоматизации рабочих процессов, основанная на событийной модели (event-driven architecture). В отличие от жесткого написания скриптов на Python или Node.js, n8n визуализирует поток данных в виде графа узлов (DAG — Directed Acyclic Graph). Каждый узел принимает на вход массив объектов JSON, трансформирует их или совершает внешнее действие (API-запрос, запись в БД), и передает результат следующим узлам.

### Пошаговые действия:
1. Обзор интерфейса: рабочий холст (Canvas), панель узлов, панель выполнения (Executions).
2. Понятие элементов данных: каждый узел n8n оперирует массивом `items`, где каждый элемент — это JSON-объект вида `{ json: { key: value } }`.
3. Создание первого ручного запуска через Manual Trigger и вывод тестового сообщения через узел Edit Fields.

### Конфигурация / Код:
```json
{
  "status": "success",
  "event": "initial_workflow_test",
  "timestamp": "2026-10-18T12:00:00Z"
}
```
> **Инсайт:** Всегда помните: n8n обрабатывает массивы данных пакетно (batch processing). Если на вход узла пришло 10 объектов, узел выполнится 10 раз, если не включена агрегация.

## Урок 02: Сравнение платформ: n8n vs Make (ранее Integromat)
**Модуль:** `1` | **Цель:** Понять фундаментальные различия в архитектуре, ценообразовании и безопасности между n8n и Make.
**Ключевые узлы:** `Webhook`, `HTTP Request`

### Теория и механика:
Сравнение ключевых факторов:
1. Хостинг: Make — исключительно проприетарное облако (SaaS). n8n — гибрид (есть n8n Cloud и бесплатный Self-Hosted на своем VPS/Docker).
2. Модель тарификации: Make тарифицирует каждую операцию (Execution Operation). В сложных циклах и опросах API бюджет Make быстро исчерпывается. n8n тарифицирует запуски сценариев (Workflows Executions) в облаке, а на Self-Hosted — полностью безлимитен.
3. Безопасность и GDPR/HIPAA: В n8n Self-Hosted данные клиентов, токены и приватные ключи никогда не покидают ваш сервер.

### Пошаговые действия:
1. Анализ сценариев, где выгоднее Make: простые интеграции между CRM и Google Таблицами без собственного сервера.
2. Анализ сценариев, где необходим n8n: высоконагруженные процессы, передача чувствительных данных, сложные AI-агенты с локальными LLM и базами векторов.

### Конфигурация / Код:
```json
# Пример конфигурации запуска n8n через Docker Compose:
services:
  n8n:
    image: docker.n8n.io/n8nio/n8n
    ports:
      - '5678:5678'
    environment:
      - N8N_HOST=n8n.yourdomain.com
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=https://n8n.yourdomain.com/
```
> **Инсайт:** Для AI-агентов n8n предпочтительнее благодаря нативным узлам LangChain, поддержке векторных хранилищ и полному контролю над окружением Node.js/Python.

## Урок 03: Cloud vs Self-Hosted
**Модуль:** `1` | **Цель:** Разобрать плюсы и минусы облачной версии n8n Cloud и самостоятельного развертывания на собственном сервере.
**Ключевые узлы:** `Docker`, `PostgreSQL`, `Environment Config`

### Теория и механика:
n8n Cloud избавляет от необходимости администрировать сервер, обновлять образы и настраивать SSL-сертификаты. Однако Self-Hosted развертывание на базе Docker на виртуальном сервере (Hetzner, DigitalOcean) за $5-10 в месяц дает неограниченное число рабочих процессов, параллельных потоков и полный доступ к файловой системе сервера.

### Пошаговые действия:
1. Выбор хостинга (минимум 2 vCPU, 4GB RAM для продакшн n8n с AI-узлами).
2. Настройка поддомена и DNS-записей (A-запись на IP сервера).
3. Установка Traefik или Nginx Proxy Manager для автоматического выпуска SSL-сертификатов Let's Encrypt.

### Конфигурация / Код:
```json
docker run -d --name n8n -p 5678:5678 -v ~/.n8n:/home/node/.n8n docker.n8n.io/n8nio/n8n
```
> **Инсайт:** Всегда монтируйте постоянный том (volume) `~/.n8n`, иначе при перезапуске контейнера все учетные данные и сценарии удалятся.

## Урок 04: Самостоятельное развертывание n8n (Self-Hosting)
**Модуль:** `1` | **Цель:** Практическое пошаговое развертывание надежного production-кластера n8n с PostgreSQL.
**Ключевые узлы:** `Docker Compose`, `Postgres`, `Redis / Queue Mode`

### Теория и механика:
По умолчанию n8n использует SQLite. Для промышленной эксплуатации SQLite не подходит из-за блокировок базы при параллельных вебхуках. Промышленный стек: n8n + PostgreSQL в качестве бэкенд-БД + Redis для масштабирования очередей (Queue Mode).

### Пошаговые действия:
1. Подготовка файла docker-compose.yml с сервисами postgres и n8n.
2. Настройка переменных среды: `DB_TYPE=postgresdb`, `DB_POSTGRESDB_DATABASE=n8n`.
3. Настройка регулярного создания резервных копий (бэкап папки workflows и БД pg_dump).

### Конфигурация / Код:
```json
version: '3.8'
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: n8n
      POSTGRES_USER: n8n_user
      POSTGRES_PASSWORD: SecretPassword123
    volumes:
      - pg_data:/var/lib/postgresql/data
  n8n:
    image: docker.n8n.io/n8nio/n8n
    depends_on: [postgres]
    environment:
      DB_TYPE: postgresdb
      DB_POSTGRESDB_HOST: postgres
      DB_POSTGRESDB_USER: n8n_user
      DB_POSTGRESDB_PASSWORD: SecretPassword123
```
> **Инсайт:** Используйте режим Queue Mode с несколькими воркерами (Workers), если ожидается наплыв более 50 вебхуков в секунду.

## Урок 05: Что такое API и Webhook
**Модуль:** `1` | **Цель:** Освоить базовые протоколы взаимодействия современных интернет-сервисов: REST API и Webhooks.
**Ключевые узлы:** `Webhook Trigger`, `HTTP Request Node`, `Respond to Webhook`

### Теория и механика:
API (Application Programming Interface) — метод активного опроса (*pull*), когда n8n делает запрос к внешнему сервису. Webhook — метод пассивного уведомления (*push*), когда внешний сервис сам мгновенно присылает HTTP POST запрос на URL n8n при наступлении события (например, оплата Stripe или новое сообщение в Telegram).

### Пошаговые действия:
1. Создание вебхук-триггера в n8n (разница между Test URL и Production URL).
2. Тестирование вебхука через Postman или curl.
3. Возврат кастомного ответа клиенту через узел 'Respond to Webhook' (код 200 OK, JSON-тело).

### Конфигурация / Код:
```json
curl -X POST https://n8n.yourdomain.com/webhook/test-endpoint \
  -H 'Content-Type: application/json' \
  -d '{"event":"payment_received", "amount": 99.00, "currency": "USD"}'
```
> **Инсайт:** В режиме разработки слушайте Test Webhook (он активен только когда открыта кнопка Listen for Test Event). Для фоновой работы обязательно активируйте workflow и используйте Production URL.

## Урок 06: Что такое Node и как n8n обрабатывает данные
**Модуль:** `1` | **Цель:** Глубоко понять внутреннюю структуру данных n8n: JSON, бинарные данные, ссылки на переменные.
**Ключевые узлы:** `Code (JavaScript/Python)`, `Edit Fields (Set)`, `Item Lists`

### Теория и механика:
В n8n данные передаются между узлами строго в формате массива объектов: `[ { json: { ... }, binary: { ... } } ]`. Для доступа к данным предыдущих узлов используются выражения синтаксиса `{{ $json.fieldName }}` или `{{ $('Название Узла').item.json.fieldName }}`.

### Пошаговые действия:
1. Работа с синтаксисом выражений: конкатенация строк, математические операции, работа с датами через Luxon (`$now.toFormat('yyyy-MM-dd')`).
2. Переключение между режимами JavaScript и выражений.
3. Парсинг вложенных структур JSON и списков.

### Конфигурация / Код:
```json
// Пример кода в узле Code (JavaScript):
return $input.all().map(item => {
  return {
    json: {
      fullName: `${item.json.first_name} ${item.json.last_name}`.trim(),
      isAdult: item.json.age >= 18,
      processedAt: new Date().toISOString()
    }
  };
});
```
> **Инсайт:** Всегда проверяйте панель Schema справа от редактора выражений — там отображаются реальные поля, пришедшие из предыдущего шага.

## Урок 07: Создание простого workflow
**Модуль:** `2` | **Цель:** Собрать первый рабочий автоматический сценарий от триггера до отправки уведомления.
**Ключевые узлы:** `Schedule Trigger (Cron)`, `HTTP Request`, `Telegram Node`

### Теория и механика:
Простой линейный процесс: регулярный запуск по расписанию (Cron) -> получение данных из публичного API (например, погода или курс валют) -> форматирование сообщения -> отправка в мессенджер Telegram.

### Пошаговые действия:
1. Настройка Schedule Trigger: запуск каждый день в 09:00 утра.
2. Настройка HTTP Request: запрос к API курсов валют (JSON).
3. Создание Telegram-бота через @BotFather, получение токена и Chat ID.
4. Сборка текста сообщения и успешная отправка.

### Конфигурация / Код:
```json
<b>Курс валют на сегодня:</b>
💵 USD/UAH: {{ $json.rates.USD }}
💶 EUR/UAH: {{ $json.rates.EUR }}
<i>Данные обновлены автоматически через n8n</i>
```
> **Инсайт:** Используйте HTML-форматирование в Telegram Node для красивого визуального выделения жирным шрифтом и курсивом.

## Урок 08: Создание сложных workflow
**Модуль:** `2` | **Цель:** Научиться проектировать разветвленные сценарии с условиями, слияниями и валидацией.
**Ключевые узлы:** `IF`, `Switch`, `Merge`, `Filter`

### Теория и механика:
В реальных процессах данные ветвятся. Узел IF разделяет поток на True/False. Узел Switch направляет поток по нескольким правилам (например, по статусу заказа: New, Processing, Shipped, Cancelled). Узел Merge объединяет данные из нескольких веток (по ключу, по порядку или по совпадению).

### Пошаговые действия:
1. Реализация Switch с 4 маршрутами по полю `{{ $json.lead_type }}`.
2. Объединение параллельных веток через Merge (режим 'Combine by Position' или 'Choose Branch').
3. Обработка ситуации, когда одна из веток вернула пустой массив.

### Конфигурация / Код:
```json
// Логика Switch: 
Rule 1: {{ $json.score }} >= 80 -> VIP Lead
Rule 2: {{ $json.score }} >= 50 -> Warm Lead
Fallback: Cold Lead
```
> **Инсайт:** Если узел в одной из веток падает с ошибкой, весь workflow прерывается, если в настройках узла не включен параметр 'Continue On Fail'.

## Урок 12: Оптимизация работы на основе контекстных данных
**Модуль:** `3` | **Цель:** Обогащение запросов к LLM релевантным динамическим контекстом из баз данных.
**Ключевые узлы:** `Supabase / Postgres`, `Set`, `LLM Chain`

### Теория и механика:
Если передать модели общий вопрос пользователя без контекста, она начнет галлюцинировать. Обогащение контекстом (Context Injection) заключается в том, что перед вызовом LLM сценарий n8n достает из базы профиль клиента, историю его покупок и регламент компании, после чего склеивает их в единый расширенный запрос.

### Пошаговые действия:
1. Получение ID пользователя из входящего Telegram-сообщения.
2. Запрос к PostgreSQL: `SELECT name, tier, balance, last_ticket FROM clients WHERE tg_id = $1`.
3. Сборка контекстного блока `[CLIENT CONTEXT]` и передача в системный промпт LLM.

### Конфигурация / Код:
```json
Context Assembly Formula:
`Контекст клиента:
Имя: ${$json.name}
Тариф: ${$json.tier}
История: ${$json.history}
Вопрос: ${$json.question}`
```
> **Инсайт:** Ограничивайте длину подтягиваемой истории (например, последние 3 обращения), чтобы не раздувать размер контекстного окна и снижать стоимость вызова.

## Урок 13: Анализ сценариев (Debugging)
**Модуль:** `4` | **Цель:** Освоение инструментов отладки, поиска узких мест и инспекции ошибок в n8n.
**Ключевые узлы:** `Execution History`, `Pin Data`, `Debug Console`

### Теория и механика:
Панель Executions хранит полные логи каждого запуска, включая входные и выходные данные каждого узла, заголовки HTTP и время отклика. Функция 'Pin Data' позволяет зафиксировать тестовые данные на узле, чтобы не запускать весь процесс заново при отладке одного блока.

### Пошаговые действия:
1. Использование Pin Data для заморозки тестового вебхука.
2. Пошаговое выполнение узлов (Step-by-step test).
3. Анализ времени выполнения каждого узла для оптимизации производительности.

### Конфигурация / Код:
```json
// Проверка типа данных в консоли браузера при отладке:
console.log(typeof $json.amount, $json.amount);
```
> **Инсайт:** В production выключайте сохранение успешных выполнений (Save successful executions: Never / Error only) для экономии места на жестком диске сервера.

## Урок 14: Error Workflows и обработка ошибок
**Модуль:** `4` | **Цель:** Построение отказоустойчивых сценариев и автоматических аварийных контуров.
**Ключевые узлы:** `Error Trigger`, `Telegram Alert`, `Slack`, `Retry On Fail`

### Теория и механика:
Любой внешний API может вернуть ошибку 500, 502 или превысить таймаут. В n8n реализовано два механизма защиты:
1. Локальный: параметры 'Retry On Fail' (автоповтор запроса до 3 раз с экспоненциальной задержкой).
2. Глобальный: специальный Error Trigger Workflow, который перехватывает падение любого процесса в системе и отправляет аварийное уведомление дежурному инженеру.

### Пошаговые действия:
1. Создание отдельного Error Handler Workflow с триггером Error Trigger.
2. Привязка Error Workflow в настройках рабочих сценариев (Workflow Settings -> Error Workflow).

## Урок 25: Введение в архитектуру RAG
**Модуль:** `8` | **Цель:** Изучение концепции Retrieval-Augmented Generation для ответов по миллионам закрытых документов.
**Ключевые узлы:** `Document Loader`, `Text Splitter`, `Embeddings`, `Vector Store`

### Теория и механика:
RAG (генерация, дополненная поиском) решает три главные проблемы LLM: галлюцинации, устаревание знаний и приватность. Вместо дообучения модели (Fine-tuning), документы нарезаются на чанки, оцифровываются в векторные эмбеддинги и сохраняются в векторную базу данных. При вопросе пользователя система находит семантически близкие фрагменты и передает их модели в качестве подтвержденного контекста.

### Пошаговые действия:
1. Общий конвейер RAG: Ingestion (Загрузка) -> Chunking (Нарезка) -> Embedding -> Vector DB -> Retrieval (Поиск) -> LLM Generation.
2. Понятие векторного пространства и косинусного сходства (Cosine Similarity).

### Конфигурация / Код:
```json
RAG Query Prompt Template:
Ответь на вопрос пользователя, используя ТОЛЬКО факты из предоставленного контекста.
Если ответа нет в контексте — честно скажи 'Я не нашел информации в регламенте компании'.

КОНТЕКСТ:
{context}

ВОПРОС: {question}
```
> **Инсайт:** Никогда не отправляйте в модель весь документ целиком — RAG находит именно релевантные абзацы, экономя 95% стоимости токенов.

### Конфигурация / Код:

# Вектор выглядит как массив float чисел:

Качество RAG на 80% зависит от качества предобработки сырых данных (Garbage in — Garbage out). Если в документ попадут навигационные ссылки сайта, баннеры и футеры, векторный поиск будет сбиваться. Перед векторизацией данные необходимо конвертировать в чистый структурированный Markdown.

### Пошаговые действия:
1. Парсинг веб-сайта через HTTP Request и конвертация HTML в чистый Markdown.
2. Извлечение метаданных документа (автор, категория, дата, URL источника).
3. Запись метаданных в векторное хранилище вместе с текстом (Metadata Filtering).

### Конфигурация / Код:
```json
Metadata Schema for Vector:
{
  "source_url": "https://help.company.com/shipping",
  "document_type": "faq",
  "updated_at": "2026-10-01",
  "access_level": "public"
}
```
> **Инсайт:** Фильтрация по метаданным позволяет искать документы только конкретного отдела или за определенный год.

## Урок 30: Продвинутая нарезка текста (Advanced Chunking)
**Модуль:** `8` | **Цель:** Освоение семантического чанкинга и нарезки по смысловым блокам.
**Ключевые узлы:** `Code (Custom Splitter)`, `Markdown Splitter`

### Теория и механика:
Слепая нарезка по количеству символов часто разрывает таблицы, списки и логические блоки. Advanced Chunking использует структуру документа (заголовки `#`, `##`, `###`) или семантический анализ (смена темы) для формирования логически завершенных чанков.

### Пошаговые действия:
1. Использование Markdown Header Text Splitter: разделение документа строго по заголовкам H2 и H3.
2. Сохранение контекста заголовков внутри каждого чанка (Header Inheritance).
3. Специальная обработка строк таблиц.

### Конфигурация / Код:
```json
// Пример структуры чанка с сохранением заголовка:
`[РАЗДЕЛ: Возврат средств -> Сроки]
Срок возврата денежных средств составляет от 3 до 5 рабочих дней.`
```
> **Инсайт:** Никогда не разбивайте короткие таблицы на части — чанк должен содержать шапку таблицы и все связанные строки.

## Урок 31: Hybrid Search: объединение векторного и ключевого поиска
**Модуль:** `8` | **Цель:** Максимальная точность извлечения данных за счет гибридного поиска (BM25 + Dense Vectors + Reranking).
**Ключевые узлы:** `Hybrid Retriever`, `Cohere Rerank`, `Supabase pgvector / Qdrant`

### Теория и механика:
Векторный поиск (Dense Retrieval) отлично ищет по общему смыслу и синонимам, но плохо находит точные артикулы, номера договоров и аббревиатуры. Ключевой поиск (BM25 / Sparse) ищет точные совпадения слов. Hybrid Search объединяет оба метода, а нейросетевой реранкер (Cohere Rerank) ранжирует итоговый список по релевантности.

### Пошаговые действия:
1. Настройка гибридного индекса в векторной базе данных (Dense + Sparse векторы).
2. Подключение модели переранжирования Cohere Rerank Node (выбор 3 лучших из 20 найденных).
3. Сравнительное тестирование: 100% точность нахождения артикулов и технической терминологии.

### Конфигурация / Код:
```json
Hybrid Formula (Reciprocal Rank Fusion - RRF):
RRF_Score = (1 / (60 + Rank_Vector)) + (1 / (60 + Rank_BM25))
```
> **Инсайт:** Использование реранкера повышает релевантность ответов RAG-системы на 25-35% на сложных технических регламентах.
